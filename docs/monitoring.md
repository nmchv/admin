# Мониторинг, пользователи, журналы

## Как работает мониторинг

Workflow `.github/workflows/monitor.yml` по расписанию (каждые 5 минут) запускает `monitor/check.mjs`. Скрипт:

1. запрашивает список целей у `cc_monitor_targets` (URL сервисов, пути проверки, пороги из Settings);
2. делает HTTP-запросы с таймаутом и одним повтором;
3. отправляет результаты в `cc_record_health` (там же открываются/закрываются инциденты и пишутся логи — только при смене состояния);
4. проверяет эндпоинты Supabase (database / api / auth).

Реальный интервал берётся из **Settings → Сервисы и мониторинг** (минимум 5 минут): более частые запуски workflow пропускаются. Ручной запуск с флагом `force` — Actions → monitor → Run workflow.

Статусы: `unavailable` — нет ответа/5xx/таймаут, `degraded` — ответ медленнее порога, `operational` — всё хорошо. Uptime = доля проверок, не обнаруживших недоступность. Если последняя проверка старше `max(3 × интервал, 15 мин)`, статус показывается как «Нет данных» — монитор мог остановиться.

## Настройка

1. Примените `supabase/migrations/0004_monitoring_users_settings.sql`.
2. **Settings → Сервисы и мониторинг → Выпустить токен** (только владелец). Значение показывается один раз; в БД хранится только sha256-хэш.
3. GitHub → репозиторий → Settings → Secrets → Actions → `MONITOR_TOKEN` = токен. Там же должны быть `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`.
4. Заполните URL сервисов (Services → Изменить). Сервисы без URL не проверяются.
5. Запустите workflow вручную с `force`, убедитесь, что данные появились в Monitoring.

## Ограничения (честно)

- GitHub Actions cron не гарантирует точность: запуски могут запаздывать на минуты, а в периоды нагрузки пропускаться.
- GitHub отключает scheduled workflows в репозитории без активности 60 дней — делайте коммит или включите workflow заново.
- Это HTTP-проверки снаружи. CPU, память и диск сервера недоступны; для Supabase проверяется только доступность эндпоинтов.
- Уведомления — только внутри панели (колокольчик). E-mail/мессенджеры не реализованы.

## Пользователи

Раздел Users показывает агрегаты без персональных данных. «Посетители» (Analytics) — анонимные, «зарегистрированные» — аккаунты Supabase Auth без администраторов. Чтобы появилась разбивка по сервисам, приложение после входа пользователя вызывает:

```js
await supabase.rpc('cc_register_service_user', { p_service: 'geotrainer' });
```

Функция привязывает текущего авторизованного пользователя к сервису (идемпотентно, обновляет «последняя активность»).

## Журналы

- **События системы** — единый журнал (`cc_system_logs`): фильтры по категориям, сервису, датам, поиск, пагинация, детали с метаданными.
- **Действия администраторов** — `cc_admin_activity`: кто и что менял, включая входы, выдачу/отзыв прав, выпуск токена.

## Администраторы

Settings → Безопасность. Выдать/отозвать доступ может только владелец; пользователь должен уже существовать в Supabase Auth. Публичной регистрации нет. Последнего владельца и себя отозвать нельзя (проверка на сервере).
