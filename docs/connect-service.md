# Подключение сервиса к Control Center

Существующие приложения автоматически не изменяются — подключение выполняется отдельным шагом в каждом репозитории.

## 1. Регистрация

Сервис должен быть в реестре: **Services → Добавить сервис** (или строка в `cc_services`). Идентификатор (`slug`) после создания не меняется — по нему приложение запрашивает своё состояние. Укажите URL — он нужен для мониторинга (этап 4).

## 2. Страница обслуживания

Добавьте **первым скриптом в `<head>`** приложения (до всех остальных скриптов):

```html
<script src="https://admin.nmchv.ru/maintenance.js" data-service="SLUG"></script>
```

Где `SLUG` — идентификатор сервиса, например `geotrainer`. Скрипт сам знает адрес Supabase и публичный anon-ключ (подставляются при сборке Control Center).

Для приложений на Vite/Astro вставьте тег в `index.html` / общий layout.

### Как это работает
1. До отрисовки скрипт скрывает страницу и вызывает публичную RPC `cc_get_maintenance(slug)`.
2. Если на сервисе (глобально или индивидуально) включено обслуживание — страница полностью заменяется заглушкой **SYSTEM MAINTENANCE** с сообщением и ожидаемым временем восстановления. Сообщение выводится как обычный текст (HTML не интерпретируется).
3. Состояние перепроверяется каждые 20 секунд и при возвращении на вкладку. Когда обслуживание снято — страница перезагружается сама.
4. Скрипт сообщает панели, что заглушка подключена (RPC `cc_guard_ping`). Пока сигнала нет, в карточке сервиса и в окнах включения обслуживания показывается предупреждение «Заглушка не подключена».

### Приоритет
Глобальное обслуживание (если сервис не исключён) → индивидуальное → штатная работа.

### Что именно закрывается
- **Интерфейс сайта** — заглушкой (`maintenance.js`). Её нужно подключить на каждом сайте, иначе при нажатии кнопки сайт продолжит открываться.
- **База данных** — на сервере: миграция `0006` ставит на таблицы сервиса RESTRICTIVE-политику RLS `cc_maintenance_block`. Пока сервис на обслуживании, `anon` и `authenticated` не могут читать и писать его таблицы, даже в обход заглушки. Администраторы панели доступ сохраняют.
  Таблицы сервисов: `exam_trainer` — `attempts`, `attempt_tasks`, `attempt_answers`, `task_progress`, `task_answer_keys`, `exam_scoring_rules`; `tutor` — `tutor_*`; `geotrainer` — `geotrainer_*`; `forms` — `forms_*`. Общие таблицы аккаунта (`profiles`, `user_settings`, `projects`, `notifications`) не блокируются: вход в аккаунт должен работать всегда.
- **Портал** — статус проекта в таблице `projects` автоматически переключается на `maintenance` и возвращается к прежнему после снятия режима.

### Ограничения (важно)
- **RLS должен быть включён** на таблицах сервиса, иначе политика не ставится (миграция выводит NOTICE со списком таких таблиц).
- **Запросы через SECURITY DEFINER-функции** (RPC) обходят RLS. Если сайт работает с данными через такие функции, добавьте в них проверку `public.cc_maintenance_gate('slug')`.
- **Fail-open на первом визите:** если состояние неизвестно (первый визит и Supabase не отвечает), приложение работает как обычно; скрытие страницы снимается не позже чем через 2,5 с. Если сервис был закрыт, а Supabase временно не отвечает, заглушка остаётся (последнее известное состояние хранится до 6 часов).
- Пользователь с отключённым JavaScript заглушку не увидит (но база закрыта на сервере).
- GitHub Pages кэширует `maintenance.js` до 10 минут; само состояние обслуживания запрашивается напрямую из Supabase и кэшу не подвержено.

## 3. Проверка
1. Включите обслуживание сервиса в Control Center.
2. Откройте приложение — должна появиться заглушка (в течение секунды).
3. Выключите обслуживание — страница перезагрузится в течение 20 секунд.
4. В карточке сервиса не должно быть предупреждения «Заглушка не подключена» (после первого визита на сайт).
